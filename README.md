# 值班交接体系（Oncall Handover Kit）

一套用来解决**「交接班时信息丢失」**的完整工具包：原理 → 风险清单 → 可填的交接单 → 值班看板 → 落地推广路径。

## 为什么做这个

我在一份 7×24 值班的岗位上待了一年多。这一年里经历过几次 P1 级故障，其中一次网络中断让我印象最深——不是因为它多严重，而是因为**我作为现场的人，看到的全是症状，看不到病因**。

我知道连接数归零了，但不知道是哪条链路断了；我知道告警在刷屏，但不知道主备链路已经同时失效。这些信息，是我事后从别的岗位问来的。

后来复盘才想明白：问题不在某个人的能力，而在**信息在交接时断层了**。

值班的人站在"症状层"，而"病因层"的信息分散在网络、系统、厂商等其他岗位手里——**交接班是这两层之间唯一的桥**。这座桥一旦断了，症状层的人就只能靠猜和问。

这份工具包就是把这座桥修起来：一张能填的表、八类不能漏的信息、一个把故障域放进同一屏幕的看板。

> 顺带一提，项目里还附了一篇 [`docs/network/`](docs/network/github-access-troubleshooting.md) 的网络排障记录——因为"能不能把代码推上去"本身也是个网络问题，而它用的正是这套分层排除的思路。

## 它解决什么问题

值班交接是故障处置链条里**唯一完全依赖"人的记性和嘴"**的环节，也是事故高发的时间点。典型症状：

- 上一班说"业务挂了"，接班的人以为是应用问题，实际断在链路层
- 上一班说"恢复了"，实际只是告警不报了
- 为了绕开故障临时改了配置，交接没说，接班的人维护时拆掉 → 二次故障
- 运营商/云服务商有故障公告，上一班看过了，接班的人不知道，在自己这侧白查一小时

**根因不是"没交接"，是"传了症状，没传上下文"。**

这套工具的目标只有一句话：

> **让接班的人在 60 秒内建立正确的判断方向，而不是靠问人。**

## 三分钟上手

### 只想用交接单（最常见）

打开 `templates/值班交接单模板.xlsx`：

1. 先看 **「使用说明」** 页（1 分钟）
2. 看 **「示例」** 页，那是一份填好的示范（数据全部虚构）
3. 复制 **「交接单」** 页用，每班填一次，约 2 分钟
4. 每次交接往 **「交接记录」** 页补一行，三个月后它就是你说服组长的证据

填不完就先填三栏：**未闭环事件、临时规避措施、未知项**。

### 想看一眼「值班视图」长什么样

**方式一：零依赖预览（推荐，只需要 Python）**

```bash
cd demo
python mock_exporter.py          # 保持这个窗口开着
# 另开一个窗口，用浏览器打开 preview.html
```

页面下方有四个按钮：`正常` → `延迟劣化` → `链路中断` → `恢复`，按顺序点一遍，
就是一次真实网络故障的完整形状。

**方式二：完整版（Prometheus + Alertmanager + Grafana，需要 Docker）**

```bash
docker compose up -d
```

然后打开：

| 地址 | 内容 |
|---|---|
| http://localhost:3000 | Grafana「值班视图 · 交接与故障上下文」 |
| http://localhost:9090/alerts | Prometheus 告警状态 |
| http://localhost:9093 | Alertmanager（看抑制效果） |
| http://localhost:9100/state | 假指标生成器当前状态 |

同样用 `http://localhost:9100/control?scenario=degrade` 这类地址切换场景。

## 这套东西里，有三个不那么显而易见的设计

### 1. 「主备同时中断」这个指标，大多数团队没有

大多数监控只有「主链路 down」和「备链路 down」两条告警，
**没有「两条同时 down」**——而只有这个状态才意味着：

> 自动切换必然失效，因为切换的前提是存在可用路径。

这通常说明主备走了同一物理路由（同一人井/同一管道/同一运营商）。**伪冗余比没有冗余更危险**，因为它让人误以为安全。

规则见 `prometheus/rules/oncall-rules.yml` 里的 `LINK_BOTH_DOWN`。

### 2. 告警要分层，因为「症状层」会淹掉「病因层」

断网瞬间，几十个应用同时超时，几百条告警涌进来，**最先响的那条（链路质量劣化）被淹没**。

所以规则按 `layer="application"` / `layer="network"` 打标，Alertmanager 里配抑制：

```yaml
# 网络层严重告警存在时，抑制全部应用层告警
- source_matchers: ['severity="critical"', 'layer="network"']
  target_matchers: ['layer="application"']
```

效果：值班的人看到的不是 200 条应用告警，而是那一条「主备全断」。

### 3. 看板要放「交接上下文」，不只是监控指标

值班视图右上角那个「交接待跟进」面板，就是把 Excel 交接单接进看板的位置。
**监控告诉你有多少告警，交接单告诉你还有多少事没闭环。**

真实落地时，这个数字可以来自：
- 手工填（在 Grafana 里用一个 text 变量或 json 数据源）
- 或者从工单系统/交接单服务里导出一个指标

## 数据合规

**这个包里没有任何真实数据。** 所有主机名、IP、数值都由 `demo/mock_exporter.py` 随机生成，
Excel 里的示例也是虚构的通用场景。

如果你要在公司环境里用：

- **不要**把真实告警明细、IP、主机名、业务系统名导进这个 demo
- **不要**把生产环境的截图放进这个仓库
- 真实落地时，取数脚本应当**只做聚合统计、不落明细**（见 `docs/03-落地指南.md` 的思路）

## 怎么改成你自己的

| 想改什么 | 改哪里 |
|---|---|
| 交接单字段 | `tools/build_handover_xlsx.py` 里的 `SECTIONS`，改完重跑脚本 |
| 自检清单 | 同文件里的 `SELFCHECKS` |
| 告警阈值 | `prometheus/rules/oncall-rules.yml` |
| 看板面板 | Grafana 里改完 → Dashboard settings → JSON Model → 覆盖 `oncall-view.json` |
| 故障剧本 | `demo/mock_exporter.py` 的 `collect()` 函数 |

重新生成 Excel：

```bash
python tools/build_handover_xlsx.py
```

## 这套东西对你的价值（说实话）

它不会立刻让你涨薪。它能给你三样东西：

1. **一个能讲的故事**：「我发现值班最大的问题是信息在交接时断层，所以我做了一套结构化的交接体系。」
2. **一个能拿出手的产出**：Excel 模板 + 看板 + 方法论，可以放 GitHub，可以给面试官看。
3. **一个组内的位置**：从「值班的」变成「会做体系的人」。

**不要一上来就说"我们要改交接流程"。** 先自己填两周，只给自己看。
详见 `docs/03-落地指南.md`。

> 交接的三条铁律：
> **现象和判断必须分开写。**

> **必须写「我还不确定什么」。**
